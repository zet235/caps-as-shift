# CapsAsShift security and code review

## Scope and result

Two independent, read-only reviewers examined the C++ sources, build script,
tests, README, design and implementation plan. One reviewed security, the
other correctness. There is no Git repository or commit range in this folder.

- **Security:** no confirmed Critical, High or Medium vulnerability identified
  for normal, non-elevated use in a same-user Windows desktop threat model.
- **Correctness:** four important lifecycle defects were found. All four were
  reproduced in an isolated test harness and then fixed; the full build passes.
- **Acceptance still needed:** physical keyboard/IME behavior, elevated windows,
  lock/unlock, sleep/resume, and actual Explorer restart/login.

The reviewers examined the pre-fix version. The fixes, English UI and newly
embedded icon were validated locally; there was no second independent review.

## Important findings — fixed

### 1. Failed synthetic release could be forgotten during shutdown

The old mapper cleared its source state after a failed Shift-up. If shutdown
ran before the queued error handler, `StopHook` saw no held state and never
retried release.

**Fix:** `src/keyboard_mapper.cpp:38–46` tracks the outstanding output release
separately. Every cleanup route uses `mapper.stop`, including the error route;
a failed cleanup keeps its release obligation for a subsequent attempt.

### 2. An inherited injected Shift could leave Caps mapping disabled

`GetAsyncKeyState` does not distinguish physical and injected input. Previously
the startup sample was stored as a confirmed physical hold; an injected release
was ignored, leaving the hold set and preventing subsequent Caps transitions.

**Fix:** inherited startup state is distinct from physical state
(`src/keyboard_mapper.hpp:19–27`). An external left-Shift release reconciles only
the inherited state (`src/keyboard_mapper.cpp:20–24`); confirmed physical holds
and the app's output obligations remain separate.

### 3. Exit released left Shift while the user was still holding it

The previous cleanup unconditionally injected Shift-up for any held source,
including a native left Shift or an inherited startup hold.

**Fix:** cleanup hands a held native modifier back to Windows and releases a
Caps-only synthetic hold (`src/keyboard_mapper.cpp:38–46`). Coverage includes
Caps-only, left-only, both held and inherited-hold shutdown.

### 4. Autostart read failure removed the Exit menu

`ShowMenu` returned immediately on a registry read failure, hiding the only
ordinary shutdown control along with the optional startup setting.

**Fix:** `src/main.cpp:76–96` still constructs the menu, disables the unavailable
startup item, and leaves Exit usable.

## Verification

`tests/lifecycle_test.cpp` exercises the real mapper and app cleanup/menu code.
Only desktop/registry API boundaries are substituted: it does not inject keys,
show dialogs or change the user's registry. Before the fixes it reported four
failures matching the important findings. Afterward all 11 lifecycle checks pass.

The final `powershell -NoProfile -ExecutionPolicy Bypass -File .\build.ps1`
also passed the three existing C++ test programs, generated the nine-size ICO,
compiled the Windows resources, built the EXE and passed the GUI smoke test
(tray icon, duplicate launch and Exit). `objdump -p` shows only Windows/UCRT
dependencies, without dynamic MinGW runtime DLLs. The generated PNG was visually
checked, and no Chinese strings remain in the application sources.

## Deferred low-priority findings

### Security hardening

- **Same-integrity menu-command messages** (`src/main.cpp:136–145`): another
  same-user process can send the autostart command. It can only toggle this app's
  fixed path, and normally already has direct HKCU write access. This is not a
  demonstrated privilege escalation. Dispatching the selected action directly
  would reduce the exposed message surface.
- **Registry allocation bound** (`src/autostart.cpp:20–43`): a same-user writer
  could provide an oversized startup string. Rejecting lengths inconsistent with
  the expected command before allocation would harden availability. No memory
  corruption or runtime resource-exhaustion attack was demonstrated.

### Reliability

- The smoke test's window lookup does not verify PID ownership and checks tray
  readiness only once (`tests/app_smoke.ps1:27–60`). A competing launch or slow
  startup can invalidate its assumptions. A future improvement should verify
  ownership and poll readiness before controlling the window.
- The Run-key command is not checked against Microsoft's documented
  260-character command limit (`src/autostart.cpp:61–65`). A very long path may
  be written successfully without working at login.
- Existing Caps Lock toggle state is preserved. The README now explains how to
  exit, turn it off and relaunch.
- Rebuilding a running EXE fails at the linker. The README now instructs users
  to exit before building; automatic early detection is still absent.

## Limits and judgments

- Lock/secure-desktop transitions may hide a physical release from a
  desktop-scoped hook. This requires desktop reproduction before selecting a
  reconciliation policy.
- The hook and shell/registry operations share a thread. A long stall could
  trigger Windows' low-level-hook timeout; no guaranteed timeout was found or
  reproduced. A dedicated hook thread is not added on speculation.
- Physical key ordering, NumPad/extended-key interactions and the user's IME
  cannot be established by sender stubs or static inspection.
- There is no guarantee of cleanup after forced termination or coordination
  with arbitrary third-party remappers. Windows input-injection privilege
  restrictions still apply.
- No key-history logging or networking was found. Signing, compiler provenance,
  installation ACLs and supply-chain auditing were not established by this review.
